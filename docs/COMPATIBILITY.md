# 兼容性设计

DSH 是一个"一切皆插件"的宿主：主题、侧栏、输入框、模型、会话、压缩后端都可能是第三方实现。所以兼容性不能靠"测试时没冲突"，只能靠**不假设**。

本文按三类风险分别写死规则：宿主层共存、界面层不占位、非 UI 入口。

---

## A. 宿主层（已实现）

### A1. 别人也在处理同一个错误

`agent/request-error` 是瀑布事件（waterfall）：每个监听器拿到 `next()`，返回决定即终止后续。

本插件的顺序是**先 `next()`，再自己决定**：

```
await next() → 有决定就原样返回
            → 没有决定，才检查是不是上下文溢出
```

含义：

- 排在它前面或后面的策略先表态，它不抢；
- 别的插件（例如自动重试、自动审核）已经处理过的错误，它不会重复处理；
- 两个插件同时"兜底"时，各自的重试次数都是有界的，不会形成无限互相重试。

**残余风险**：如果另一个插件在 `next()` 之后**不调用 `next()`** 就返回 `undefined`，瀑布被截断，本插件收不到。这是 DSH 瀑布语义，不是本插件能单方面修复的；文档里明确写出，便于排查。

### A2. 压缩后端被替换或缺失

`ctx.get('compaction')` 是**可选能力**：

| 情况 | 行为 |
|---|---|
| 后端正常 | 调用 `compactIfNeeded(agent, 'context-overflow', signal)` |
| 后端被换成第三方实现 | 照常调用；签名不符会抛错，被捕获并降级为警告 |
| 没有压缩后端 | 不注册行为，只在首次溢出时记一条警告 |
| 后端正忙（另一次压缩进行中） | 抛 `ManualCompactionError('busy')`，捕获后放弃本次重试 |

插件从不自己实现压缩，因此**压缩策略升级不需要跟着改**。

### A3. 子代理与多会话

重试次数按 `agent` 记在 `WeakMap` 里：

- 每个子代理是自己独立的 agent，各有自己的上界；
- agent 被回收后记录随之消失，不泄漏；
- 不会因为"主会话已经试过"就放弃子代理的救援。

### A4. 版本变更

只依赖两处公开面（见 `DESIGN.md`）。任何一处改名或改签名，表现是**装载期或调用时明确报错**，而不是静默改变行为。

### A5. 重复安装 / 双份加载

同一 profile 里同一个包只会有一条装载行。若用户误把插件同时以 `link:` 与 `github:` 安装，DSH 会在装载期报重复 id，而不是让两个实例同时挂监听。

## B. 界面层（v0.2 起生效的硬性规则）

v0.1 没有浏览器半区，**与主题、布局、侧栏完全无关**。从 v0.2 引入水位条开始，遵守以下规则：

### B1. 位置来自槽位，不来自 DOM

- 只用 `ctx.slots.inject('conversation.input.dock', () => ctx.slots.register(...))`；
- **禁止** `querySelector`、`document.body.appendChild`、按类名找输入框；
- 槽位是宿主声明的扩展位，主题/皮肤只改样式，不移动槽位。

### B2. 不占别人的位置

- `order` 取不抢占的区间（计划 30）：低于 activity/usage 这类内置条，高于需要靠前的告警；
- 只占流内高度，**不设** `position: fixed`、不大幅提升 `z-index`；
- 不注册全局 CSS；类名统一前缀 `dsg-`，避免污染主题与其它插件。

### B3. 颜色跟随主题令牌

- 只用 `--dsw-*` 语义令牌，不写死色值；
- 明/暗主题、第三方主题都应自动适配；对比度按 WCAG AA 校验；
- 状态色（正常/提醒/危险）走语义令牌，而不是直接把红黄绿写进组件。

### B4. 槽位消失就安静消失

输入区是组合出来的：`conversation.composer`（chain）→ `conversation.composer.bar` → `conversation.input.dock`。任何一环被别的插件接管（例如结构化提示词这类接管输入框的插件），dock 都可能不挂载。

规则：**组件不挂载即视为用户不需要这条展示**，宿主逻辑（溢出救援）照常工作，不报错、不降级成 DOM 注入。

### B5. 数据缺失时渲染空

会话未打开、还没拿到用量、跨设备连接刚重置——一律渲染空，不抛异常、不占位、不显示"加载中"超过一帧。

### B6. 移动端 / 窄窗口

`dsh-pocket` 这类手机访问、或窗口很窄时：水位条压成单行、可折叠，不横向撑破输入区。

## C. 非 UI 入口：IM、远程、headless

QQ/微信/飞书/钉钉（`dsh-im` 一类）、远程访问、`--profile headless` 走的是**同一个 agent loop**，因此：

| 事实 | 结论 |
|---|---|
| `agent/request-error` 在宿主进程触发，与有没有浏览器无关 | **v0.1 的救援在这些入口天然生效** |
| 插件按 profile 安装，不是全局 | 跑 agent 的那个 profile 里必须也装本插件 |
| IM 桥通常有自己的错误回传格式 | 救援成功后用户收到的是正常回答；救援失败仍由桥决定怎么显示 |
| 远程/多端共用同一会话 | 重试按 agent 计，不按浏览器标签计，多端同时看不会重复救援 |

**部署提醒**：如果你用 `desktop` profile 跑桌面端、另起一个 profile 跑 IM 网关，两个 profile 都要装。

## D. 与已知插件的共存（推断，待实测）

| 插件 | 关系 | 预期 |
|---|---|---|
| `dsh-context` | 都读上下文，互不写 | 兼容 |
| `billion-context` | 若它替换了压缩后端 | 我们调用的是当时生效的后端，兼容；它压完之后我们通常不再触发 |
| `dsh-cost-meter` | 都只读用量 | 兼容 |
| `dsh-streamfold` | 它做 DOM 层折叠，我们 v0.2 在槽位 | 视觉相邻，需实测 |
| 结构化提示词类（接管 composer） | dock 可能不挂载 | 我们的 UI 自动消失，宿主逻辑不受影响 |
| `dsh-im` / 远程 | 同一 agent loop | 宿主逻辑有效；注意 profile 安装位置 |
