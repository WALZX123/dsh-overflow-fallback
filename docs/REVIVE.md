# 会话续命（revive）设计

目标：**上下文把会话聊死之后，原会话一个字不丢，新会话接着干。**

这是本插件真正的产品形态。兜底重试（`lib/index.js`）只是它的前置条件：先争取原地救活，救不活才续命。

---

## 1. 用户看到什么

上下文超限、且强制压缩之后仍无法发送请求时：

1. 原会话**保持原样**，可随时打开查阅（只读，不迁移、不删除）；
2. 自动生成一份**交接包**（`lib/handoff.js`）：你要继续的事、最后的结论、动过的文件、用过的工具；
3. 在同一个工作目录下新开一个会话，交接包作为第一句话放进去；
4. 新会话的标题/元数据标明它是从哪个会话续来的；
5. 用户在新会话里直接说"继续"即可，不需要重新讲一遍背景。

失败路径：生成或新建失败时，只把交接包交到用户手里（复制/保存），不假装成功。

---

## 2. 为什么不是"分叉"

DSH 的 fork（`meta.isSeeded` + `inheritedEventCount` + 父会话前缀 seed）复制的是**原始历史**。问题在于：这段历史本身就是超限的——分叉出来仍然超限，等于把病一起搬走。

所以续命走的是**摘要式冷启动**：新会话只带一条交接消息，历史留在原会话里可查。代价是细节不会全部带过去，这是有意的取舍。

---

## 2.5 有损，但可回查

必须直说：**交接包是有损的**。它是摘录，不是摘要，更不是全文。会丢的东西包括：

- 中间的推理过程与试错；
- 工具的原始输出（只保留了文件路径和调用计数）；
- 措辞细节、当时的判断依据。

不会丢的只有一样，但这一样最关键：**原会话的完整日志仍在磁盘上**，DSH 可以随时重新打开。溢出毁掉的是"这个请求还能不能发出去"，不是"历史还在不在"。

所以续命的承诺不是"不丢内容"，而是**不丢可访问性**：

1. 交接包末尾给出原会话 ID 与轮次锚点（`T3@seq42`），指向具体位置；
2. 新会话里的人和模型都能据此回到原会话查细节（下一步：注册只读回查工具，走 `sessionQuery` / `sessionReference`）。

为什么不是"让模型总结一遍"：

- 仍然有损，而且**可能编造**——摘录至少忠于原文；
- 压缩失败的原因往往就是"没有可压缩区间"或"摘要请求本身失败"，再发一次摘要请求大概率同样失败；
- 多一次模型调用，就多一次花费与延迟，还会把原会话内容再送去一次 provider。

真正的"不遗漏"只有一条路：**别让它溢出**——更早压缩、更小的工具结果、更少的长文本重读。那是上游压缩类插件的职责，不是救援插件的。

## 3. 技术路径

### 3.1 生成交接包（已实现）

`lib/handoff.js` 是纯函数，零 I/O、零模型调用、输出有上界（6000 字符）：

```js
buildHandoff({ events, title, sessionId, reason })
// → { markdown, stats: { requests, conclusions, files, tools, turns } }
```

它只读事件流：`user/message`（只取人工输入，跳过注入）、`assistant/message`、`tool/call` 的 `arguments` 里的路径字段。畸形数据一律跳过，不抛错。输出末尾固定包含「原文在哪」：原会话 ID 与 `T<轮次>@seq<序号>` 锚点。

### 3.2 新建会话（待接线）

宿主侧 `ctx.agents.create()` 接受完整的种子事件：

```ts
ctx.agents.create({
  sessionId,
  meta: { cwd, parentSession: <原会话 id>, origin: undefined },
  seed: [<一条 user/message 事件，内容为交接包>],
  agentOptions: { provider, model },
})
```

`session/created` 会在新会话插入后触发，Web 客户端的会话列表由 `api-session-controller` 监听该事件，因此新建的会话会出现在列表里。

### 3.3 待验证的点（接线前必须确认）

| 问题 | 为什么要先验证 |
|---|---|
| `user/message` 种子事件的精确字段 | `SessionEvent` 是持久化格式，字段错了会污染会话日志 |
| `agentOptions` 能否继承原会话的 provider/model | 否则新会话可能落到默认模型 |
| `cwd` 从原会话的 `header.meta.cwd` 读取 | 新会话必须留在同一工作目录，否则工具全失效 |
| 新会话是否自动出现在 Web 列表、能否自动跳转 | 决定体验是"一键续命"还是"要用户自己找" |
| 归档/子代理会话要不要允许续命 | 归档会话续命会破坏用户的组织意图 |

在这些点确认之前，插件**不会**在生产路径里创建会话——写坏一个会话日志的代价，远大于晚一个版本上线。

### 3.4 触发方式

| 方式 | 说明 |
|---|---|
| 自动（默认关，可开） | 兜底重试失败后直接续命，适合 IM / headless 这类没人守在屏幕前的入口 |
| 手动 | 在错误卡片/设置里提供"续命"动作；Web GUIt 下更可控 |

配置（默认 `manual`）：

```yaml
config:
  enabled: true
  maxAttempts: 2
  revive: manual     # off | manual | auto
```

- `off`：只做兜底重试，不注册任何动作；
- `manual`：注册模型工具 `revive_session` 与服务方法 `reviveFor()`，由人或模型显式触发；
- `auto`：重试次数用尽后，自动新建会话并注入交接包。

`auto` 的额外约束：**子代理会话不续命**（`meta.origin === 'subagent'`），同一个会话只续一次（`WeakSet`）。

## 4. 安全与边界

| 面 | 约定 |
|---|---|
| 原会话 | **只读**。不 append、不迁移、不删除 |
| 新会话 | 只写一条交接消息；之后由用户正常对话产生 |
| 内容 | 交接包来自原会话自己的日志，不外发、不调用模型 |
| 体积 | 单份交接包 ≤ 6000 字符；每段引文 ≤ 320 字符 |
| 敏感信息 | 交接包会包含原会话里的文本。默认不落盘；若用户选择保存，由用户决定位置 |
| 失败 | 生成失败 → 只返回错误；新建失败 → 把交接包给用户手动使用；注入失败 → dispose 掉半成品 agent 再抛错 |
